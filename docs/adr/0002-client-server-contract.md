# ADR 0002: Client-server contract (thin client)

**Status:** Accepted
**Date:** 2026-10-04
**Supersedes:** — (расширяет ADR 0001)

## Context

ADR 0001 зафиксировал: сервер — единственный источник истины (server-authoritative).
Этот документ уточняет **что именно** клиент имеет право делать, а что — нет.

Цель: клиент — **тонкий**. Он вводит команды и рисует снапшоты. Он не симулирует мир.

## Decision

### Клиент имеет право

1. **Читать input** — клавиатура/мышь, локальные состояния UI (открыт ли чат/инвентарь).
2. **Отправлять команды серверу** через `internal/client/net/actions.go`:
   - `PlaceRocket`, `BoardRocket`, `ExitRocket`, `RocketInput`
   - `ThrowSpear`, `HitMob`, `HitMammoth`
   - `CraftItem`, `CraftFactory`, `PickupItem`
   - `PlantSeed`, `WaterPlant`, `TakeWater`
   - `TameMammoth`, `SaddleMammoth`, `RideMammoth`, `LeashMammoth`
   - `PlaceHouse`, `PlaceBoat`, `PlaceSolar`, `PlaceBattery`, `PlaceFactory`
   - `SelectItem`, `AcceptContract`, `OpenFactory`, `ToggleDoor`
3. **Рисовать снапшот** — получает `protocol.Snapshot` 20 Hz и отображает.
4. **Интерполировать между снапшотами** — для плавного рендера в промежутке между тиками.
5. **Локальный UI-стейт** — открытые меню, положение курсора, набранный текст чата.

### Клиент НЕ имеет права

1. **Не симулирует физику** критичных объектов (ракета, мобы, снаряды, мамонты).
   - Исключение: интерполяция `Pos`/`Vel` между снапшотами — **только для рендера**.
2. **Не принимает решений** о попадании, крафте, краже лута — только шлёт команды.
3. **Не хранит истину о мире** — `a.world` это **кеш последнего снапшота**, не источник.
4. **Не вычисляет game-state** (HP, топливо, инвентарь) — читает из снапшота.

### Контракт `RocketInput`

Клиент шлёт **только намерение**, не состояние:

    type RocketInput struct {
        Thrust    float32  // -1..+1 (клавиши Space/Ctrl)
        TargetUpX float32  // куда хочет смотреть (мышь/WASD)
        TargetUpY float32
        TargetUpZ float32
        AutoPilot string   // "" | prograde | retrograde | radial_out | radial_in | normal | antinormal
    }

Сервер:
- интегрирует физику (гравитация, тяга, атмосфера)
- плавно поворачивает `Up` к `TargetUp` со скоростью `steerRate`
- публикует новое состояние ракеты в снапшоте (Pos, Vel, Up как DX/DY/DZ)

Клиент:
- **не** интегрирует физику ракеты
- **не** хранит `Fuel`, `Apoapsis`, `Periapsis` — читает из снапшота
- синкает позицию игрока к ракете (Pos + Up * 1.5) **из снапшота**, не из локальной симуляции
- крутит `TargetUp` локально (это UI-решение, не game-state)

### Что делать при рассинхроне

Если клиент видит расхождение (например, нарисовал ракету в точке A, а в новом снапшоте она в точке B):
1. **Рендер** интерполирует к B за один тик.
2. **Логика** никогда не полагается на A — только на B.
3. Никаких "предсказаний" (prediction) — их нет в архитектуре.

## Consequences

### Положительные

- **Anti-cheat by construction**: клиент не может соврать о позиции/топливе/попадании,
  потому что он их не считает.
- **Нет desync**: у всех клиентов один источник (snapshot).
- **Reconnect работает из коробки**: клиент после реконнекта получает снапшот и рисует.
- **Тестирование**: `Server` тестируется без клиента; `Client` тестируется с mock-сервером.

### Отрицательные

- **Latency отклика**: между нажатием Space и видимым движением ракеты — 1 RTT + 1 tick (~50–100 мс).
  Для PvE-кооп на 32 игрока — приемлемо. Для PvP-шутера — нет.
- **Никакого prediction**: на плохой сети управление ощущается "тяжёлым". Митигация —
  interpolation рендера + небольшой input buffer.
- **Клиент обязан интерполировать**: без этого ракета будет дёргаться между тиками 20 Hz.

### Открытые вопросы

- **Интерполяция**: сейчас клиент рисует снапшот как есть. Нужна ли линейная интерполяция
  между двумя последними снапшотами для Pos ракеты? Возможно — отдельная задача.
- **Input buffer**: сейчас `RocketInput` шлётся каждый кадр. Может ли клиент шлёт только
  изменения? Это оптимизация, не архитектура.

## Migration notes

Что нужно удалить с клиента (для соответствия контракту):

1. `internal/client/app/rocket.go` — если там есть **симуляция** (интеграция `noseX/Y/Z` во времени),
   её надо удалить. Крутить `TargetUp` локально — можно, это UI.
2. Любые попытки хранить `Fuel`, `Apoapsis` и т.п. на клиенте — должны читаться из снапшота.
3. `syncPlayerToRocket` должен брать позицию **из снапшота**, а не из локального расчёта.

Проверка: если убить TCP-соединение, клиент **не должен** продолжать движение ракеты —
он должен замереть в последней точке из снапшота.
